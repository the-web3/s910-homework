——————————————————————————接口传输模式——————————————————————————
1. http和websocket

http协议是单向，无状态的，每次请求需要带上身份和参数，而且是一问一答的形式，需要先请求，再相应。
websocket是全双工通信，先用http做一次升级握手，之后两边都可以以随时推消息。
比如行情和消息推送，需要服务端马上吧变化推送给客户端就更适合websocket

2. rest 和 graphQl

rest核心是通过URI获取特定的资源
rest缺点，极度依赖api文档，而且容易获取数据不足或者过度。
graphQl 可以通过服务端公布的schema组合需要的资源。

3. rpc

不同rest和graphQl
rpc不需要定义路径，只需要像调用函数一样调用服务端，rpc机制会提供stub函数给客户端调用。

grpc是实现rpc的一种
在grpc中使用propotcol buffers定义服务的名称和函数

json-rpc 是远程函数调用，方法名和参数装在一封固定的 JSON 里。它不生成 stub，客户端自己拼这段 JSON 就行

| | 接口怎么定 | 线上的数据 | 谁在用 |
| --- | --- | --- | --- |
| REST | 每个资源一个路径，用 HTTP 方法表示动作 | 每个接口自己定的 JSON | 对外的增删改查 |
| JSON-RPC | 一个地址，函数名写在 `method` 里 | 固定信封的 JSON | 链节点、浏览器直接调用 |
| gRPC | `.proto` 生成 stub | protobuf 二进制 | 内部微服务 |


————————————————————————时序数据库和Doris——————————————————————————————

1. 时序型数据库
时序型数据库主要处理时间戳+各种指标的场景。适合行情，监控等场景。主要的有InfluxDB、TimescaleDB、Prometheus。
doris是实施数仓，不是时序型数据库，但是有时序向能力：
    按时间做分区，并用动态分区自动建分区、按 TTL 删过期数据
    compaction_policy = time_series，按时间局部性合并小文件，适合日志和连续写入
    ASOF JOIN，按时间找「当时最近的一条」，例如某笔成交对应的最新报价
所以适合做聚合行情。

| | 模型 | 消息会不会丢 | 适合 |
| --- | --- | --- | --- |

1. Kafka

基本概念：
Kafka 里的数据是一份只追加的日志。消息进 topic，topic 再切成多个 partition。每条消息在分区里有一个递增的 offset。
生产者只负责往 topic 写。消费者按 offset 拉，不是 broker 推。
同一个 consumer group 里，一个分区同时只会被一个消费者读，所以一条消息在组内只处理一次。另一个系统要再读同一份数据，换一个 group 即可，从自己的 offset 开始。

使用方法：
先起 broker（开发时常用一个节点）。业务上定 topic，比如 `trades`。
生产者带一个 key 写入。消费者用固定的 `group.id` 拉消息，处理完再提交 offset。
同一交易对要保证顺序时，key 用 symbol，这样同一 symbol 总是进同一个分区。分区内部有序，分区之间没有顺序。


使用注意点：
- offset 提交早了，进程在写库前崩掉，这条就丢了。提交晚了，重启会再读到一次。下游按成交 id 去重。
- `acks=all` 要等副本都写上，慢但少丢。`acks=0` 或 `1` 更快，leader 挂了可能丢。
- 消费跟不上时不要只加消费者个数。消费者数超过分区数，多出来的会空闲。要先加分区。
- Kafka 能留历史，但不是数据库。retention 要设，过期的流水会删。
- 重平衡时分区会换人，处理中的消息可能再投一次，业务要幂等。


2. Redis

基本概念：
Redis 有三种常见的「当队列用」的方式，差别很大。
- List：`LPUSH` 写入，`BRPOP` 阻塞取出。取走就没了，像一个任务栈。
- Pub/Sub：`PUBLISH` 给频道，当前在线的订阅者立刻收到。没人订、或者订的人掉线，消息直接丢掉，不积压。
- Stream：`XADD` 追加，消费组用 `XREADGROUP` 读，处理完 `XACK`。没确认的会留在待处理列表里，可以重新分配。这是三种里最接近消息队列的。

使用方法：
最新价广播给在线服务，用 Pub/Sub，频道按交易对拆，比如 `ticker:BTC-USDT`。
要保证处理完才算数，用 Stream，先 `XGROUP CREATE` 建消费组，worker 读到后写库，成功再 ack。
一次性的短任务（发一封通知）可以用 List。

使用注意点：
- Pub/Sub 不做持久化。订阅者重启后，中间的行情不会补发，只能再去拉一次快照。
- List 里 `BRPOP` 成功但业务还没做完就崩了，这条任务找不回来。
- Stream 不 ack 会堆在 PEL 里。要有人扫超时未确认的消息，用 `XAUTOCLAIM` 转给别的消费者，不然会一直占着。
- Redis 数据在内存里。没开 AOF 或 RDB，进程挂了队列一起没。也不适合拿来存很久的历史成交，内存比磁盘贵，回放用 Kafka。
- 一个 Redis 既当缓存又当队列时，队列突发会把内存打满，缓存开始被淘汰。队列要单独限制长度（Stream 的 `MAXLEN`）。

3. MQTT

基本概念：
MQTT 是发布订阅协议，消息体很小，适合设备和不稳定的网络。角色就三个：发布者、订阅者、broker（常见的有 Mosquitto、EMQX）。双方都不直连，都连到 broker。
主题用 `/` 分层，比如 `quote/BTC-USDT`。订阅时 `+` 匹配一层，`#` 匹配后面所有层。`quote/+` 能收到每个交易对的一层主题，`quote/#` 会把这个前缀下的全部收走。
QoS 决定送达：
- 0：发出去就不管，最多一次
- 1：至少一次，broker 没收到确认会重发，可能重复
- 2：恰好一次，来回确认最多，也最慢

使用方法：
设备或行情服务作为客户端连上 broker，带一个唯一的 clientId。
推最新价就 `Publish` 到对应主题。App 或下游服务 `Subscribe` 自己关心的主题。
需要知道客户端是不是异常掉线，可以在连接时设遗嘱（LWT）：连接还在时遗嘱不发，连接被 broker 判定断开后，broker 替它发一条「已离线」。


使用注意点：
- clientId 相同，后连上的会把前一个踢下线。每个进程要有自己的 id。
- clean session 为 true 时，离线期间的订阅和未送达消息不保留。要补离线消息，会话得保留，QoS 还得是 1 或 2。
- `quote/#` 这种大订阅会把所有交易对都推过来，客户端要接得住，不然 broker 会堆积然后断开。
- QoS 2 只保证协议这一层不重复，业务上仍要用成交 id 做幂等。下单这种不能只靠 QoS。
- retain 为 true 时，broker 会留下该主题最后一条。新订阅者一订上就能拿到，适合「当前价」，不适合「每一笔成交」。
- 公网的 broker 要开账号和 TLS。1883 明文端口不要直接暴露。


4. RabbitMQ

基本概念：
RabbitMQ 走 AMQP。生产者不把消息直接塞进队列，而是发给 exchange，由 exchange 按规则路由到队列，消费者再从队列拿。
exchange 有四种常用类型：
- direct：routing key 完全相等才进队列
- fanout：忽略 key，绑到这个交换机的队列都收到一份
- topic：key 按 `.` 分词，`*` 匹配一个词，`#` 匹配零个或多个词。`trade.*` 能匹配 `trade.BTC-USDT`
- headers：按消息头匹配，用得少
队列可以持久化。消费者默认要手动 ack，没 ack 的消息在连接断开后会重新投递。

使用方法：
声明交换机、队列，再用 binding 把两者绑起来，并写上 routing key。
行情成交可以用 topic 交换机：写 Doris 的服务绑 `trade.*`，告警服务绑 `trade.BTC-USDT`，各拿各的。
消费者把 `autoAck` 关掉，处理成功再 `Ack`。失败就 `Nack`，并决定是重新入队还是送进死信队列。


使用注意点：
- 路由没绑上时，消息默认直接丢掉。重要的交换机要加备用交换机（alternate exchange）把没路由到的消息接住。
- 持久化要三处一起做：交换机、队列、消息（`DeliveryMode=Persistent`）。只做队列，broker 重启后消息还是没了。
- `autoAck=true` 表示消息一发出去就算成功。消费者刚拿到、还没写库就崩了，这条就丢了。
- 要设 prefetch。不设的话，一个慢消费者会把队列里的消息全领走，其他 worker 空着。
- 消费失败如果一直 `requeue=true`，毒消息会反复回到队头，后面的消息都过不去。失败几次后进死信队列，人再去看。
- 消费者和连接断开会被当成失败，未 ack 的消息会再次投递。同一条可能处理两次，写库要幂等。
